# Agent Note: Trusted remote devices reach the privileged /api methods

Status: implemented

English | [中文](2026-08-19-trusted-remote-privileged-actions.zh.md)

## Problem

The web GUI's `/api` privileged method set — native host dialogs (`host.pickDirectory`, `host.openPath`), the whole settings and credential configuration plane (`settings.describe`/`openDocument`/`update`/`replace`/`mutate`, `credentials.describe`/`set`/`unset`), `llm.discoverModels`, and the agent-preset authoring methods — passed the browser-trust fence with an empty trust list, which pinned it to loopback even on a deployment that declared `trustedHosts`. Two [configuration-plane](2026-07-30-config-plane-boundaries.md) and [draft-discovery](2026-08-04-draft-provider-endpoint-interrogation.md) decisions chose that pin because `trustedHosts` is a DNS-rebinding fence, not authentication, and no authentication layer exists yet.

The consequence is that a person running `dsh web` on one machine and reaching it from their own phone or laptop over a private tunnel — the reported case is a Mac reached from an iPhone over `tailscale serve` — could browse and prompt sessions, and could pick a workspace directory through the in-app browse picker (whose `list`/`create` operations are not in the privileged set), but could not use the native OS directory dialog, open or edit settings, manage credentials, or discover models. Those are exactly the remaining setup actions a remote-first user needs. The loopback pin made the ordinary `/api` surface — including the in-app browse picker — usable remotely while fencing off the native dialogs and the configuration surface, with no way to opt in.

## Decision

The privileged method set passes the same trust fence against the configured `trustedHosts` allowlist as every other `/api` call, rather than against an empty (loopback-only) list. On a deployment that declares trusted authorities, a request whose `Host` is loopback or a declared `trustedHosts` entry — and which carries no untrusted `Origin` and no `sec-fetch-site: cross-site` marker — reaches these methods; every untrusted or rebound `Host` is still refused with 403 before dispatch. The DNS-rebinding and cross-site fences (`packages/client/connection/src/api-request-trust.ts`) are unchanged; only the loopback-only pin on the privileged branch in `apply` (`packages/client/connection/src/index.ts`) is relaxed to honor `trustedHosts`.

Which methods are privileged, and that reading configuration counts as privileged, are unchanged from the config-plane decision this partially supersedes. `credentials.describe` still reports only whether a named environment reference is configured and where it resolves from — its metadata, never the secret value. The model catalog (`llm.providers`, `llm.models`) and `agentPreset.list`/`select` remain outside the privileged set.

This is a partial supersession, scoped to a personal trusted-device deployment. `trustedHosts` remains a DNS-rebinding reachability fence, explicitly not authentication: it distinguishes a trusted authority from a rebound name, not one device or person from another. Every device that can both reach the server on the network and present a trusted `Host` header therefore holds the full privileged authority — it can read the settings plane, probe named credential references, set and unset credentials, drive native host dialogs, and make the host fetch caller-chosen URLs. This relaxation does not add authority beyond what a session already grants: the default agent carries `bash` and the filesystem tools, so any caller that may start a session can already run commands as this process. That existing capability is the trust assumption the deployment already makes; it is evidence that the same trust already applies here, not a proof that admitting remote devices is safe. The deployment is appropriate only when every allowed device is trusted as an administrator of this process. The bind stays loopback-only (`--host 0.0.0.0` is refused), and no public tunnel — Tailscale Funnel, a public reverse proxy, or any Internet-facing forward — may front it, because the fence cannot distinguish a public visitor who reaches the server and presents the right `Host` from the operator. This note cannot certify a deployment's tunnel ACLs; that obligation stays with the operator.

## Alternatives considered

- **Keep the loopback pin; document the limitation.** Rejected: it leaves a remote-first user unable to reach the native dialogs, settings, credentials, or model discovery — the setup actions the in-app browse picker does not cover — with no opt-in short of editing source.
- **A `--directory-picker`-style per-method force flag.** Rejected as heavier than the need: the privileged set already shares one fence, and the user's request is to admit their own trusted devices to all of it, not to toggle individual methods.
- **An authentication layer (tokens, per-device identity) now.** Deferred, not rejected: token minting, storage, and rotation are real product surface. This change closes the usability gap for a trusted-device deployment without pre-deciding that design; a real auth layer is the condition under which the shared-authority caveat here goes away.
- **Per-connection adaptivity (privileged for a loopback-origin request, denied for a remote one).** Rejected: a tunnel forwards as loopback or as the trusted authority, so the request origin cannot separate a local browser from a remote trusted one — the same reason the [directory-picker default](../feature/2026-08-19-web-directory-picker-default-browse.md) stopped reading a loopback bind as proof of a local operator.

## Consequences

- On a `trustedHosts` deployment, a trusted remote device reaches every privileged method: the native OS directory dialog and `host.openPath`, the settings and credentials pages, model discovery, and agent-preset authoring. The in-app browse picker was already reachable and is unchanged. Plain loopback deployments are unaffected — an empty `trustedHosts` still pins the set to loopback.
- The trust surface for the whole configuration and native-action plane is now the set of devices that can both reach the server and present a trusted `Host`, shared without per-device authentication. A deployment that adds a `trustedHosts` authority reachable by an untrusted device widens that surface accordingly; the appropriate configuration is a private tunnel whose every allowed device is administrator-trusted, no public Funnel or proxy, loopback bind only.
- `credentials.describe` reachability from a trusted remote device exposes credential-reference metadata (configured-or-not and its source), not credential values.
- The connection guard's privileged-branch coverage now asserts both directions: a declared trusted authority is admitted (carrier 404 from the empty proxy proves the fence passed), and an untrusted `Host`, a mismatched `Origin`, and a `sec-fetch-site: cross-site` marker on the declared Host are each refused with 403 — over hand-assembled requests and a real HTTP server (`packages/client/connection/tests/node-half.host.spec.ts`).
- Partially supersedes the loopback-only caller restriction in [the configuration-plane boundaries](2026-07-30-config-plane-boundaries.md), [the web configuration plane](2026-07-30-web-config-plane.md), and [draft provider endpoint interrogation](2026-08-04-draft-provider-endpoint-interrogation.md); those notes keep their still-current classification of what is privileged and why, cross-linked here.
